# context_article_repo

Единый репозиторий серии экспериментов для статьи «Управление контекстом в
агентной программной инженерии: модель жизненного цикла и паттерны
проектирования».

Гипотеза серии (drift-eval — оценка на дрейфующем полигоне): контекст,
прошедший жизненный цикл (C2), дает прирост успешности агентной разработки
там, где он служит единственным носителем актуального знания — то есть
когда API полигона дрейфанул, а внутренние знания модели устарели или
отсутствуют.
Представьте автомобиль, у которого завод молча перепаял проводку: на самих
деталях новой схемы нет, в старом мануале — тем более, и единственное
место, где она записана, — сервисная книжка. Вот C2 и есть такая книжка.

Конфигурации контекста: C0 — полигон без контекста (контроль); C1 — «сырой»
корневой AGENTS.md «за 10 минут»; C2 — «после ЖЦ» (K-структура с
маршрутизацией, per-dir AGENTS.md, навык `migration-v2`, V-хуки; детали —
в `protocol/` каждого эксперимента).

## Структура

```
experiments/<name>/        — эксперимент серии (8 задач T1–T8 × C0/C1/C2 × k=5)
├── protocol/              — методика (pre-registration), сценарии T*.txt,
│                            зонд знаний модели, промпт серии
├── contexts/              — config.template.json (модель, base_url, temperature),
│                            контексты c1/c2; local-key.json — локальный ключ,
│                            в git НЕ попадает
├── scripts/               — make_workspace / run_one / batch_drift / merge /
│                            analyze / accept (детерминированная приемка)
├── skills-src/            — набор навыков для контекстов
├── results/               — runs.csv, stage_c*.csv, logs/, traces/, analysis/
├── fixture/               — полигон lab_8 (финальное состояние фикстуры, в git;
│                            билд-артефакты build/.dart_tool исключены)
├── harness/madharness-mini/ — рабочая копия харнесса с патчами серии (в git,
│                            билд-артефакты исключены)
└── workspaces/            — генерируемые workspace (локальные, в git не входят)
```

`workspaces/` (содержат инжектированный ключ API в конфиге) и
`contexts/local-key.json` — operational-активы: живут на диске
экспериментатора, в git не попадают (см. корневой `.gitignore`).

## Итоги серии (завершена)

Полигон lab_8 v3 (коммит ebf17f9) построен по схеме единственного носителя:
конвенции дрейфа (base:'USD' при default 'EUR', семантика кэш/сеть
forceRefresh, init-guard readThemeMode) удалены из всех побочных носителей
репозитория; единственный носитель — контекст C2. Зонд выводимости (3 агента
C0 на T1) в обеих сериях: 0/3 — полигон не течет.

| Эксперимент | C0 | C1 | C2 | C2−C0 | на конвенциях v2 |
|---|---|---|---|---|---|
| deepseek-flash (итерация 2, 120 прогонов) | 0,50 | 0,57 | **0,93** | +0,43 | +0,52 |
| qwen3.6-35b-a3b-mtp (120 прогонов) | 0,45 | 0,38 | **0,88** | +0,42 | +0,60 |
| qwen-fail: C2 до эволюции → после (полигон v2) | 0,33 | 0,45 | 0,35 → **0,95** | +0,60 (после) | — |

Триаж: неудач класса (1) «конвенция не сообщена контекстом» у C2 нет ни в
одной серии (deepseek 27 и qwen 30 таких — все у C0/C1, ожидаемый эффект
single-carrier). Отчеты: `experiments/<name>/results/analysis/final-report-drift.md`
(qwen — со сравнением с deepseek; qwen-fail — со сравнением итераций в
`results/analysis/iter2-comparison.md`).

Главный вывод: при невыводимом из репозитория знании прирост C2 не убывает
по силе модели — +0,43 у сильной, +0,42 у слабой. Может, тогда хватит и
«сырого» контекста? Нет: без конвенций он не помогает ни одной из моделей
(слабой — ниже контроля, интервалы перекрываются). Граница применимости —
исполнительская дисциплина агента, а не передача знания (неудачи C2 у
слабой модели: литеральные формы конвенций, досрочные завершения сессий,
многочастная документация).

Итерация qwen-fail замыкает жизненный цикл. Дефект среды исполнения
(инструмент shell без оболочки; deepseek сам нашел flutter.bat — 754
вызова в 82/120 прогонов, qwen — 0) закрыт эволюцией контекста по триажу
75 неудач (раздел «Среда исполнения»): 0,35 → 0,95, токены 819 → 512 тыс.,
время 1133 → 298 с.

## Как стартовать новую серию

Допустим, вы хотите повторить серию на своей модели или новом полигоне.
Порядок такой:

1. Скопируйте каталог ближайшего эксперимента в `experiments/<новое-имя>`
   (структура выше) или создайте с нуля по тому же шаблону.
2. Обновите `ROOT`/`KEYFILE` в `scripts/*.sh`, конфиг
   `contexts/config.template.json` (модель, base_url, temperature); методику —
   новая серия = новая пре-регистрация (`protocol/methodology.md`, правки
   только новым коммитом с указанием причины).
3. Пересоберите полигоны: `scripts/make_workspace.sh c0|c1|c2`, проверьте
   здоровье API (`scripts/api_health.py`), далее — по протоколу серии
   (навык eval-series): префлайт → фоновые батчи → слияние → анализ →
   отчет → коммит результатов.

## Итерации при эволюции C2

Если серия показывает систематические провалы C2 по дефектам контекста
(класс (1) триажа), контекст эволюционирует.

Эволюция доказательная: до решения — обязательный сравнительный анализ
трасс C0 (без контекста) → C1 (сырой AGENTS.md) → неудач C2 (паттерны:
что контекст не сообщил / сообщил не в той форме / сделал неисполнимым);
каждое изменение новой версии C2 мотивировано конкретным паттерном из
трасс.

Механика итерации: новая версия — отдельным коммитом с причиной в
methodology (раздел 10); итоги архивируются в `results/iter<N>/`
эксперимента; перезапускается только поток C2 той же моделью (C0/C1
переносятся без перезапуска); отчет обязан сравнивать итерации и
проверять, ушли ли паттерны-основания. Прецедент — эволюция
v1 → v2 в `flutter-eval-qwen-fail` (0,35 → 0,95).
